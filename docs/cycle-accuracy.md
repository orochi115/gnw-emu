# gnw-emu 离周期精确还差多少（真机测量，2026-11-04）

## 结论

- gnw-emu 现在是**功能级**模拟：每条指令固定记 4 ns，按 280 MHz 折算是 1.12 个周期；DMA、DMA2D 瞬间完成；不模拟缓存、Flash 等待周期、总线延迟。
- 真机上同一条指令的耗时从 0.5 周期（双发射）到 32 周期（`vdiv.f64`）不等，访存从 1 周期（TCM）到 236 周期（关缓存读外挂 Flash 的一行）不等。所以“改成周期精确”不是调参，而是给 CPU 和总线建时序模型。
- 测量还发现了三处**功能级**的时钟错误，应该先修，工作量以天计（第 4 节）。
  - 最大的一处：原厂固件把 CPU 跑在 **136 MHz**，模拟器按 280 MHz 驱动 SysTick，所以原厂固件的 1 ms 节拍在模拟器里只有 0.486 ms。
- 工作量估计，分四级：

| 级别 | 内容 | 估计 | 预期误差 |
|---|---|---|---|
| L0 时钟正确 | SYSCLK/HCLK/APB/定时器时钟按 RCC 计算；SysTick、TIM、DWT、icount 速率跟着变；修 TIM 的整数截断 | 2–3 天 | 定时器和节拍完全正确；指令速度仍是固定 1.12 周期/条 |
| L1 指令与访存成本 | 翻译时按指令类别累计周期数（下表），按取指区域和 Cache 开关加取指代价，加载按区域加固定延迟；DMA2D/DMA/CRYP 按测得的吞吐率延迟完成中断 | 3–4 周 | 典型代码 ±15–25%（开缓存时多数指令能对上，误差主要来自双发射配对和缓存未命中） |
| L2 缓存与总线 | 16 KB I/D Cache（行、组相联、替换）、写缓冲、AXI/AHB/OSPI 并发、LTDC/DMA 争用、Flash 预取 | 再 1.5–2 个月，运行速度降到现在的 1/5–1/10 | ±5–10% |
| L3 周期精确 | M7 六级双发射流水线、分支预测、乱序完成的加载/存储、精确的总线仲裁 | QEMU TCG 架构做不到，需要另写 CPU 模型；数月起步，ARM 没有公开完整时序，只能逼近 | — |

对这两份固件来说，L0 必须做，L1 足以让 Retro-Go 模拟器的跳帧和 CPU 占用接近真机；L2/L3 投入产出比很低。

## 1. 方法

测试程序在 `hwtest/`（用法见 `hwtest/README.md`）。用 DWT_CYCCNT 计时，每项先预热一次再测三次，取最小值；每个内核展开 64 条指令（取指测试 1024 条），减去同一区域、同一缓存配置下空循环的开销。

- **A 阶段**（不写 Flash）：固件正常开机后经 SWD 暂停，把测试程序装进 ITCM 运行，固件配好的时钟、Flash、OSPI 配置原样保留。两种环境：原厂时钟画面（136 MHz、Flash 3 个等待周期）和 Retro-Go（280 MHz、7 个等待周期，由 OpenOCD 复位后从 bank2 启动）。
- **B 阶段**（只写 bank2）：同一程序放进 bank2 末尾擦除过的扇区（0x08138000，Retro-Go 只用到 0x35E23），用来测从片内 Flash 取指。测完从备份还原 bank2，读回比对一致。
- 每种组合跑三轮。216 个指标里，原厂环境有 208 个、Retro-Go 环境有 212 个三轮之间相差不到 1%；其余是开缓存时的流式未命中（2–7%，LTDC 刷屏争用 AXI）和 Retro-Go 下用 RTC 测的 CPU 频率（Retro-Go 冷启动后 RTC 时钟精度差，3%）。
- 测试期间关掉了 MPU 和固件的 DMA 流，LTDC 照常刷屏。
- 原始数据：`hwtest/results/hw_*.bin`（结果表）、`*.json`（解码后）、`*.log`（OpenOCD 输出）；模拟器的对照是 `emu_*.bin`。

## 3. gnw-emu 与真机对比

- 所有指令都记 1.12 周期。开缓存时真机的简单整数指令快一倍（双发射），乘除、浮点、分支、访存慢 2–30 倍。
- 关缓存或从外挂 Flash 读数据时，真机慢 5–200 倍。不过两份固件实际都开着缓存，所以影响主要在缓存未命中的代价。
- 中断进出：真机 17/21 周期，模拟器 3/5。
- DMA2D、DMA、OSPI 间接读写在模拟器里都是瞬间完成，CPU 和这些外设并行的时间窗口（例如 Retro-Go 一边用 DMA2D 画屏一边跑模拟器）没有体现。

## 4. 测量发现的功能性问题（建议先修，L0）

1. **CPU 时钟写死 280 MHz**（`gnw.h` 里的 `GNW_SYSCLK_HZ`）。原厂固件实际用 136 MHz（PLL1：HSI 64 MHz /4 ×17 /2），SysTick 按 136 MHz 设成 1 kHz，在模拟器里变成 2.06 kHz，`HAL_GetTick()` 快了一倍，所有超时和延时只有一半长。游戏节奏靠 LTDC 帧中断，所以画面看起来没问题。修法：根据 RCC 的 PLL1/CDCFGR 算出 SYSCLK，设置时钟变化时调用 `clock_set_hz(m->sysclk, …)` 和 refclk；DWT 也跟着变。icount 的 shift 可以保持不变，指令速度不必改。
2. **TIM 时钟写死 280 MHz，且有整数截断**（`gnw_timer.c` 的 `tim_tick_ns`）。`(PSC+1)*1e9/280e6` 截成整数纳秒，PSC=0 时 3.57 ns 变成 3 ns，计数实际快到约 333 MHz。原厂的 TIM 时钟是 34 MHz（`RCC_CDCFGR2 = 0x660`：APB1 八分频，定时器时钟取 APB1 的两倍，136/8×2），Retro-Go 是 280 MHz（`0x440`：二分频再 ×2）。修法：按 RCC 算定时器时钟，用 `muldiv64` 计数，不再折算成整数纳秒周期。
3. **LTDC 固定 60 Hz**。真机按 PLL3 和时序寄存器算出原厂 60.05 Hz、Retro-Go 59.6 Hz。差别很小，但修起来简单：像素时钟 × 总宽 × 总高。

另外两个次要的：CRYP 每块耗时只有真机的一半；WWDG 只是桩，读写正常但不会复位（对模拟器来说这样更方便）。

## 5. L1 的实现思路

- **指令成本**：QEMU 的 icount 每条指令记 1。改成在 `target/arm` 翻译时按指令类别取一个成本（2.1 节的表），TB 开头一次性扣掉 TB 的总成本。成本表开缓存和关缓存各一份，翻译时按 `CCR.IC` 选。需要给 `accel/tcg` 打一个小补丁，现在是 `gen_tb_start` 按指令条数扣。
- **取指**：翻译时就知道 TB 在哪个区域（ITCM、AXI、片内 Flash、0x90000000），关 I-Cache 时按 2.2 节的表加代价；开 I-Cache 时按 L1 的近似，假设全部命中。
- **加载**：运行时地址才知道区域，可以在加载指令后插一个 helper，按区域加延迟（关 D-Cache），代价是变慢 10–30%。也可以只对固定基址的加载在翻译时估算。
- **双发射**：翻译时做简单配对（相邻两条互不依赖的 ALU 指令算 0.5），能覆盖 2.1 节的主要情况。
- **外设**：DMA2D、DMA1、CRYP 按 2.4 节的吞吐率推迟完成标志和中断。中断进出按 17/21 周期加到 icount。
- 验证：`hwtest/emu_run.py` 在模拟器里跑同一套测试，`hwtest/parse.py --compare` 和真机结果逐项对比，可以写进 pytest 作为回归。

## 6. 局限

- 每组只跑了三轮，没有覆盖开缓存时的冲突未命中、写缓冲填满、分支误预测。
- 片内 Flash 只测了数据读和顺序取指，没测分支跳转对 Flash 预取的影响。
- 外挂 Flash 只测了前 64 KiB（原厂 OTFDEC 解密区），没测 OTFDEC 关掉时的区域有没有差别。
- 中断延迟里包含了 `dsb; isb` 和两次读 CYCCNT 的开销，绝对值偏大约 4–6 周期，但真机和模拟器的口径一致。
