# Zelda 原版时钟：gwemu 与旧 legacy 音频对比

结论：有可量测的宿主重采样损失，不能把“不够清脆”全部归因于电脑扬声器。两内核在启动后的干净滴答上生成相同的 PCM；没有证据说明新内核把滴答音色算成了另一种声音。超过一分钟的补测发现：单内核内部的尾部也会变化，两者共享同样的线性衰减斜率，不能仅凭尾巴长短判断模拟错误。09:00整点音效频谱高度相似，但时间与样本没有完全对齐，因此也不能宣称整个声音实现等价。没有实机录音或数字音频采集，无法确定硬件与软件各占多少。

## 输入、产物与方法

2026-11-16，在 macOS arm64 使用本地两个既有产物：旧 `build/qemu-system-arm`（2026-11-11 构建），当前 `build/gwemu/qemu-system-arm`（manifest revision `57b2b378e2001f20a241ecbaf9ce7c8f22aae9a3`，2026-11-13 构建）。来源复核发现本地实际gwemu SHA为 `dc20c01d56a5abf682c78177bd6fff9fc603b52a20bccd0f5c48b907b43cf8ad`，与旧manifest记录的 `f41b093d…` 不匹配。因此这里的revision只代表manifest声明，不能声称该产物仍通过旧发布来源验收。测量绑定实际SHA；未重构建或修改manifest。当前源码 HEAD 已含 Windows 适配，本轮没有在用户Windows发布包或扬声器上测量，软件机制与这份本地产物的数据应分别看待。

挂载同一份 Zelda 原版内/外部 Flash 的新副本、同一 UID，RTC 固定为 2026-01-01 09:00:00。源文件 SHA256 在每轮前后核对不变。gwemu 读取现有 `GNW_AUDIO_TAP` 的 DMA PCM，legacy 读取机器自带的 raw WAV；另外均使用 QEMU WAV 后端捕获宿主混音输出。正式 clock 捕获不按 TIME，避免已进入时钟后再次按键切换模式。

采样率均解码为 48003 Hz、16-bit mono。legacy 用既有 realtime/icount 启动方式，gwemu 用现行普通 TCG 方式；这是实际默认路径对比，不是 CPU 调度完全受控的硬件等价实验。各片段17秒，留存实际启动参数、截图、日志、JSON、原始PCM和WAV。旧内核截图有09:00数字，本地Nov13 gwemu截图未显示这些数字；音频分析以对应脉冲为依据，不宣称画面等价。

证据目录为工作区根 `out/gnw-clock-audio-20261116/`。`capture.py` 可复验；`metrics.json`、`rate-metrics.json`、`timing-metrics.json` 保存结果，`provenance.json` 保存二进制SHA、manifest和源哈希复核。

## 两个内核生成的滴答

默认48k宿主捕获中，前5个声音事件在对齐后逐样本一致（RMSE=0、SHA256相同）。其中第2/3次是没有衰减尾巴的干净滴答：

| 指标 | gwemu raw | legacy raw |
| --- | ---: | ---: |
| 固件采样率 | 48003 Hz | 48003 Hz |
| 脉冲样本数 | 799 / 800 | 799 / 800 |
| 时长 | 16.645 / 16.666 ms | 16.645 / 16.666 ms |
| 峰值 | 1066 | 1066 |
| 去均值 RMS | 452.725 / 450.065 | 相同 |
| 主要频谱峰 | 约10.71 kHz | 相同 |

这些脉冲在额外44100/48003宿主采样率实验中仍具有相同raw SHA。它们是高频成分丰富的短脉冲，重采样和播放设备的高频响应都可能影响听感。不是低频正弦测试可以充分代表的内容。

legacy 将mono复制成左右声道，gwemu直接开mono voice。以相同单声道WAV后端测量，两者峰值均为2132；这是QEMU内部mono复制、mono输出时左右相加造成的共同增益。A/B导出已将宿主WAV除以2，避免把这次测试的mono混音增益误认成新内核音量变化。桌面默认输出是stereo，不能照搬mono WAV的两倍增益。

## 确认的重采样损失

`desktop/src/core/gwemu-command.ts` 只选择 CoreAudio/SDL3，没有设置输出采样率。QEMU `audio/audio.c::audio_validate_per_direction_opts` 默认开启固定混音设置，输出44100Hz；`audio/rate_template.h` 使用相邻样本线性插值。两内核走同类QEMU音频混音路径；已有相同48000Hz实验中，即使raw相同，重采样相位不同也会改变宿主WAV。

对两次相同的干净滴答，三次独立捕获，扣除mono混音增益后得到：

| 宿主WAV频率 | 交流RMS相对raw | 8–16kHz频段功率变化 |
| --- | ---: | ---: |
| 44100 Hz（桌面默认值） | -1.63 / -1.68 dB | -1.59 / -1.61 dB |
| 48000 Hz | -1.19 / -1.22 dB | -1.23 / -1.22 dB |
| 48003 Hz（匹配固件） | 0 / 0 dB | 0 / 0 dB |

48003Hz下对齐的host PCM与raw逐样本一致，提供了取消这层插值后损失消失的单变量证据。这些数值针对两次具体脉冲、此后端和采样相位，不能作为所有滴答或真实扬声器的固定衰减量。

因此仅把44100改为48000，仍会有48003→48000的插值；48k在这两次脉冲中略好，但不能保证完全保留高频。值得优先评估的是改进重采样器，或让QEMU混音率跟随客体，并明确宿主设备是否还进行第二次转换。48003Hz WAV是对照证据，不表示电脑声卡能以此频率无转换播放，也不建议把所有固件统一硬编码为48003Hz。

## 长段时序的未关闭差异

15次完整声音事件只有最初5次完全一致。随后gwemu脉冲序列发生分叉，部分约16ms脉冲变短，带正向衰减尾巴的事件也不完全相同。legacy raw事件间隔均值约1.00005秒，gwemu该轮约0.99254秒。这是raw音频流位置的间隔，不能直接等同于真实扬声器墙钟节奏，更不能只根据这个数值判断RTC错误。

这里的“长段”指约17秒的捕获，不是长时间运行后的稳定性结论。以同一轮48000Hz宿主输出实验的raw PCM为例：

| 声音事件 | gwemu时长 | legacy时长 | 对齐后的波形 |
| --- | ---: | ---: | --- |
| 第2次 | 16.645 ms | 16.645 ms | 逐样本相同 |
| 第6次 | 16.374 ms | 60.163 ms | 前780个样本相同，后续长度和衰减尾部不同 |
| 第9次 | 28.665 ms | 16.666 ms | 长度和样本值均不同 |

事件边界按绝对幅度大于5的样本检测，超过60ms的空隙划分为下一事件；表中时长包含检测到的衰减尾部，不全部代表高频滴答本体。将两段的第1次事件起点对齐后，gwemu第15次事件在raw流中约提前97ms。上面的间隔均值使用第2至第15次事件之间的13个间隔。这些变化不同于前面重采样造成的高频损失：它们在进入宿主混音前的PCM中已经存在，但尚未证明导致了用户感受到的“不够清脆”。

gwemu检查点的`dropped_bytes`均为0；`starvation_callbacks`表示没填满请求容量，不能据此宣称可听断音。仅加icount并未让全部事件变为一致。额外开启已有实验性`gnw-h7b0-dma.timing-mode=on`反而没有生成PCM（WAV仅44字节，三个检查点production/consumption均为0），因此它不适合作为本问题的修复开关。

这批17秒记录可以确认波形不同，但不能单独判定尾部差异异常；以下超过一分钟的补测进一步缩小了结论。剩余时序差异尚不能将其根因定为DMA、RTC、固件调度或客体缓冲更新；也不能把它未经验证解释成时钟动画的其它音效。旧内核不是实机精确度基准。若继续修复，应单独跟踪DMA完成/客体填充和RTC触发的时间关系，先建立对应的失败用例。

## 超过一分钟与09:00整点补测

用户提出“不同秒的音效可能不同”后，两边从同一个`2026-01-01T08:59:45`起点运行100虚拟秒，覆盖09:00整点和09:01。仍使用同源镜像副本与同一UID，宿主WAV设为48003Hz，另外捕获raw PCM，排除前一节的重采样因素。两个native实际SHA与第一批一致，源镜像在结束后复核不变。

`long_capture.py`每约250ms只读RTC TR/DR并记录raw文件位置。事件标签采用起点之后首个记录的RTC秒数，秒边界仍有约250ms量化不确定性，不能把这些标签当作样本精确的触发时刻。两边记录均跨08:59:45至09:01:24，raw时长分别为99.574秒与99.844秒，各识别出98个声音事件；raw时长不含启动前尚未生成PCM的时间。

### 尾巴会变化，但不符合每分钟固定秒数对应固定尾长

同一个内核在下一分钟相同秒附近，声音事件的长度也不同。例如：

| 内核 | 09:00:08附近事件 | 09:01:08附近事件 |
| --- | ---: | ---: |
| legacy | 60.205 ms | 16.686 ms |
| gwemu | 16.374 ms | 28.936 ms |

因此，用户指出“不能拿不同秒的尾巴直接判断模拟错误”是必要的纠正。不过，这份录音也不支持简单的“每分钟第N秒固定播放同一尾长”的解释；它不排除固件根据场景、状态或波形相位改变声音。

更明确的共同特征是尾部的衰减方式。对普通滴答的单调尾部进行线性拟合，两者斜率均约为每样本`-0.507812`个16-bit PCM幅度单位，拟合R²接近1。gwemu识别出55个这类尾部，legacy为50个。以两边均存在的尾部为例：

| 尾部起始幅度 | 衰减至检测阈值附近的时长 |
| --- | ---: |
| 1066 | 约43.5 ms |
| 914 | 约37.3 ms |

尾巴长短与淡出的起始幅度相对应。约16.7ms的高频滴答结束后，有时接这条线性淡出，有时很快归零；因此60ms的完整事件不代表高频滴答被持续拉长到60ms。两内核在这层表现出相同的衰减规律。这些是原始PCM中的观察，尚未反汇编确认固件如何选择末端幅度或随机状态，不能据此证明所有声学行为等同于真机。

### 整点长音效相近，仍有细小时序差别

最长的连续事件在两边均对应09:00:00，波形有明显的正负振荡，区别于普通滴答的短脉冲及单向尾部。

| 指标 | gwemu | legacy |
| --- | ---: | ---: |
| 最长连续声音事件 | 1593.650 ms | 1601.400 ms |
| 绝对峰值 | 2285 | 2285 |
| 对齐起点后完全一致的前缀 | 2394样本，约49.872 ms | 相同 |

gwemu该事件约短7.750ms（约0.48%）。以50Hz频率分箱比较整段的功率谱，余弦相似度为0.99995，主要频率分布高度接近。0.3/0.5/0.7/0.9秒附近100ms窗口的主峰分别约621/438/415/658Hz，两者一致；靠近换音位置的窗口会因时间偏移取到不同音符，整段PCM没有逐样本一致。频谱相似不证明每个音符的时间、相位和瞬态一致，也不直接等同于主观听感。

这次gwemu第5至95虚拟秒间产出的PCM约89.959秒，检查点`dropped_bytes`均为0。存在小幅生产/时间差异，但没有将其根因定位到某个外设，也没有证明它造成“不够清脆”。这次补测后，应将“尾长不同”从单独的异常证据降为波形变化现象，保留对时序和宿主重采样的独立调查。

补测证据位于工作区根`out/gnw-clock-audio-20261116/zelda-{gwemu,legacy}-long-085945-run2/`，包括100秒raw/host录音、RTC日志、截图和`events.csv`。汇总为`long-metrics.json`、`long-comparison.json`及`long-same-rtc.csv`。各目录的`hour-raw.wav`导出整点连续事件，前后各加250ms静音；`hour-context-raw.wav`保留约08:59:58至09:00:05的上下文，均直接取raw PCM，未做响度归一化。未进行主观试听。

## 硬件因素与可听对照

两个实现均从DMA缓冲读取PCM送到宿主，没有模拟真机音频输出电路、扬声器与机壳的频率响应/瞬态。电脑的扬声器、耳机和系统音效处理当然可以改变清脆程度，但本轮没有实机或宿主扬声器录音，不能测出这部分贡献。

可在同一播放设备、同一音量下听以下四秒片段（宿主mono增益已归一化，未做响度归一化）：

- 默认44.1k输出：`out/gnw-clock-audio-20261116/zelda-gwemu-clock-44100/ab-host.wav`
- 同轮固件原始PCM：`out/gnw-clock-audio-20261116/zelda-gwemu-clock-44100/ab-raw.wav`
- 匹配48003Hz输出：`out/gnw-clock-audio-20261116/zelda-gwemu-clock-48003/ab-host.wav`

实际播放器还可能重采样，试听不能代替上述PCM测量。本轮只研究和导出证据，没有修改产品音频设置或固件，没有主观试听，也没有发布新包。
