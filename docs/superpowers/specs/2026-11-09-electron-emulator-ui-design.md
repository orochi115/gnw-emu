# gnw-emu Electron 模拟器 UI 设计

日期：2026-11-09。状态：架构、传输路线、取消旧实现兼容及第一阶段 UI 流程已获用户确认。用户补充要求界面美观、现代；本文补充相应视觉规范，进入实施规划，尚未授权开始编码。

用户追加 UI 自动化控制/信息读取、专业日志管理及维护文档要求。具体方案见 [UI 自动化、日志与文档设计补充](2026-11-09-ui-automation-observability-design.md)，同属第一阶段基础能力，不新增面向普通用户的调试界面。

## 1. 背景与目标

提交 `efb9ad7c554432ec8cd9c98a16346e7180534db2` 已通过 `6cf8506` 回退。回退后的已跟踪文件与原提交的父提交一致，`tests/test_profile.py` 的 11 项测试通过。未跟踪的 `.superpowers/` 目录保留。

重新设计面向 macOS、Windows、Linux 的桌面模拟器。采用 Electron、TypeScript 应用后端、独立 QEMU 进程、QMP 控制及本机 TCP 二进制完整帧传输。正式桌面应用不依赖 Python 运行时；应用层只维护一套 TypeScript 实现。仍在使用的 Python QEMU 测试驱动和固件/镜像制作工具保留，不再承担 profile/session/settings 业务。废弃的 Python 应用实现和对应旧格式删除，不提供向后兼容或迁移工具。

当前仓库证据：

- `harness/profile.py` 实现 profile、session、settings 和启动参数；`harness/launch.py` 实现窗口启动及退出状态保存。
- `/machine` 的 `buttons` QOM 属性支持运行时设置设备按钮掩码。
- LTDC 输出默认 320×240，合成两层画面并应用背光；现有有效尺寸上限为 2048×2048。
- 本机构建可用显示后端为 none、sdl、curses、cocoa、dbus；构建脚本禁用了 VNC。VNC 基础刷新间隔为 30 ms，不能直接当作稳定 60 Hz 显示路径。
- 现有宿主播放使用 macOS AudioQueue。选用跨平台 UI 不代表音频已经跨平台。

## 2. 第一阶段范围与界面

第一阶段业务功能只有游戏主窗口、加载 ROM、制作 ROM。

- 主窗口显示当前游戏画面，不打开第二个 QEMU 窗口。未加载时显示简短提示。
- 初始画面区域按 320×240 的整数倍设置，推荐 2 倍。窗口改变大小时保持源画面的宽高比、最近邻采样和居中留边；整数倍显示优先，可在空间不足时缩小。源尺寸以收到的帧为准，不硬编码为 4:3。
- macOS 使用系统菜单栏；Windows/Linux 使用应用菜单栏。业务菜单为“文件 → 加载 ROM…”和“文件 → 制作 ROM…”。保留平台必要的退出行为，不增加最近打开、调试、设置、键位编辑或手柄配置页面。
- 加载 ROM 使用系统文件选择器，只接收新的 `.gnw.json`。选择后校验；有效时在当前窗口运行。初始键盘映射与现有命令行窗口一致。
- 制作 ROM 使用独立对话框：机型、内部 Flash、外部 Flash 必填；Bank 2、SD 卡可选；有 SD 卡时提供 spi1/ospi 接线。提供保存、保存并加载和取消。保存位置通过系统保存对话框选择。
- “制作”指组合已有镜像并写 profile，不包括编译固件、制作 SD 文件系统、打补丁或添加 Retro-Go 游戏。
- 新 profile 自动生成 UUID；器件 UID 与 profile UUID 不同。新建时 UID 为可选高级字段，留空使用现有后端默认值，不自行更改固件身份语义。
- 错误使用用户能理解的路径、字段及失败原因；底层日志用于诊断，不作为主窗口正常提示。

重启、改键、手柄和按键高亮只预留职责和接口，不在第一阶段增加对应 UI。第一阶段必须处理关闭窗口、再次加载 ROM、失焦和对话框输入边界。

### 2.1 已确认的 UI 流程

- 标题为 `gnw-emu`，运行时为 `gnw-emu — ROM 名称`。主窗口没有侧栏、调试工具栏或常驻性能数值。
- 未加载时中央显示“尚未加载 ROM”，附一行文件菜单与快捷键提示；加载中显示真实阶段，例如“正在准备镜像”，不能显示虚假的百分比。运行时让画面占据主要区域。
- 加载/制作分别使用 Ctrl/Cmd+O、Ctrl/Cmd+N，具体修饰键跟随平台。打开系统菜单或对话框释放设备按钮，关闭后恢复画面输入焦点；不自动重新按下之前释放的物理键。
- 新 ROM 校验失败时，当前游戏继续显示和运行；提示原因并允许重新选择。旧会话已经退出后的启动失败展示可恢复空态，不声称旧游戏还在运行。
- 制作对话框为单列，每个文件字段带浏览按钮；必填项完整后允许保存，失焦或提交时显示字段旁的错误，提交失败聚焦第一个无效字段。
- 底部依次为取消、保存…、保存并加载…。保存成功关闭制作对话框，原会话继续运行；保存并加载成功后关闭对话框，走统一切换流程。取消系统保存对话框返回制作表单，保留所有内容。自动补全 `.gnw.json` 后缀。

### 2.2 视觉规范：现代桌面应用

界面须作为正式消费级桌面应用设计。Game & Watch 机身外观留到下一阶段，不以终端/调试面板视觉替代主界面，也不增加与第一阶段无关的装饰和功能。

| 要素 | 规范 |
|---|---|
| 字体 | 离线可用系统 sans-serif：macOS 系统字体、Windows Segoe UI、Linux 系统 sans-serif；中文走系统字体回退。路径可用系统等宽字体 |
| 字号 | 正文 14–15 CSS px，辅助说明 13 px，字段/按钮 14 px，标题 22–24 px；正文行高约 1.5 |
| 间距 | 4/8/12/16/24/32 px 标尺；对话框内容内边距 24 px，分组间隔 24 px，字段内间隔 8 px |
| 控件 | 约 40 px 高，8 px 圆角，统一边框、内边距和 hover/pressed/disabled/focus 状态；对话框 12 px 圆角与克制阴影 |
| 浅色 | 背景 #F5F6F8，表面 #FFFFFF，正文 #18181B，辅助正文 #52525B，边框 #E4E4E7 |
| 深色 | 背景 #111318，表面 #1B1E25，正文 #F4F4F5，辅助正文 #A1A1AA，边框 #343842 |
| 强调色 | 主操作蓝色 #2563EB 配白色文字；深色焦点/链接用 #93C5FD；错误文字浅色 #B91C1C、深色 #FCA5A5 |
| 主题 | 跟随操作系统浅色/深色，首阶段没有独立主题设置菜单；游戏留边始终黑色，不改变游戏颜色/亮度 |
| 图标 | 单一 SVG 线条风格、约 18–20 px；有意义的图标配文字或无障碍标签，不用 emoji 充当功能图标 |
| 动效 | 120–180 ms 的控件反馈/淡入，仅用于 UI；尊重 reduced-motion，不用装饰性动画或全屏炫光 |

颜色、间距等使用语义 CSS tokens 统一管理。辅助文字保持可读对比度，普通文字至少 4.5:1；错误不只依靠颜色表达。交互有清晰键盘焦点，Tab 顺序符合表单顺序，状态/错误通过适当 live region 通知。

制作表单视觉上分为机型/必需镜像、可选镜像、高级选项三组。器件 UID 折叠在高级选项；SD 接线随 SD 镜像启用。长路径单行省略但可查看/复制完整值，不能把原始参数名、UUID 或日志堆进正常界面。

主窗口采用原生窗口控制和平台菜单，避免首阶段自行重写拖动区域/关闭按钮。空态使用简洁的轮廓符号、短标题与一行提示；运行状态保持安静。真实阶段加载提示和错误呈现也使用同一视觉规范。

视觉验收必须查看运行中的实际窗口：浅/深色、长路径、小屏、高 DPI、加载/错误/禁用状态，以及游戏画面与制作对话框。不得仅以 DOM 存在或功能测试通过宣称 UI 已达到美观现代的要求。

## 3. 进程职责和状态归属

| 位置 | 职责 | 状态 |
|---|---|---|
| Electron 渲染进程 | 界面、像素绘制、原始键盘事件、表单 | 布局、缩放、表单、输入来源状态 |
| Electron 主进程的应用后端 | 系统对话框、文件访问、profile/session/settings、键位映射、QMP、QEMU 生命周期 | 活动 ROM、会话状态、键位配置、提交及确认的按钮掩码 |
| Electron 独立画面接收端 | TCP 接收、帧解析、有界缓冲、向渲染进程交付 | 接收中的帧、最新完整帧、尺寸和帧序号 |
| QEMU | CPU/外设、GPIO 输入、复位、像素/音频生成、工作镜像写入 | 设备真实状态 |

画面接收端使用 Node 工作线程或 utility process；实施计划根据 Electron 对传输缓冲的实际支持选择一种，不保证跨进程零复制。要求网络解析不阻塞主进程的菜单、QMP 和生命周期处理。

应用后端决定运行哪台机器和存档位置；QEMU 决定这台机器如何运行。显示传输模块使用 QEMU 的显示监听接口获取已经合成并应用背光的 surface，不在 LTDC 外设代码里直接实现网络协议。

## 4. 新文件契约和废弃实现清理

统一采用 UTF-8 标准 JSON。理由是 TypeScript 原生支持、结构校验直接，不再需要 TOML 解析器及跨语言格式兼容。配置是低频管理数据；像素仍走二进制通道。新格式使用 formatVersion=1；该版本与旧 TOML 的 version 无关，未来未知版本明确拒绝，不静默猜测。

| 文件 | 内容 |
|---|---|
| `*.gnw.json` | formatVersion、id、model、internalFlash、externalFlash；可选 bank2Flash、sdCard、sdWiring、deviceUid。只描述机器和源镜像 |
| `UserData/sessions/<id>/session.json` | formatVersion、电量 battery、USB 状态 usbPower、RTC 起点 rtc、电池/充电时长 batteryLifeMinutes/chargeTimeMinutes |
| `UserData/settings.json` | formatVersion、audio、realtime；以后按需求增加宿主 UI 偏好，第一阶段不存旧 display/recent 字段 |
| 本次运行目录中的 `state.json` | QEMU 正常退出时输出的 formatVersion、battery、usbPower；仅为设备退出快照，不包含应用配置 |

- TypeScript 独占 profile/session/settings 的解析、校验、持久化和 QEMU 参数生成。所有 JSON 文件需作结构、类型、范围及条件字段校验；JSON.parse 成功不等于配置有效。
- profile 必填 formatVersion/id/model/internalFlash/externalFlash，id 校验为 UUID，model 为 zelda/mario。新会话默认 battery=100、usbPower=false、rtc="host"、batteryLifeMinutes=480、chargeTimeMinutes=180；电量范围 0..100，时长为非负数，0 表示对应变化关闭。全局 audio/realtime 默认 true。
- profile 的镜像路径相对 profile 目录解析；sdWiring 为 spi1/ospi，只能与 sdCard 一起出现；deviceUid 为 24 位十六进制。同一个新格式 profile ID 移动位置后仍使用同一会话。
- 会话内工作副本名固定为 flash.bin、bank1.bin、可选 bank2.bin/sdcard.img，由服务根据 profile 和会话目录推导；session.json 不重复保存可推导的路径。
- 源镜像不修改；已有新格式会话的工作副本不覆盖。新建副本先写临时文件，完成后提交，失败不能留下被当成完整镜像的半成品。
- 保存配置采用原子替换。制作 ROM 每次创建新的 profile ID；覆盖已有文件由系统对话框确认，也创建新身份，不隐式继承该文件对应的存档。
- 不读取旧 `.gnw.toml`、session.toml/settings.toml，不转换旧存档，不维护旧字段或退出文本解析器。用户旧 ROM、镜像及 UserData 不批量删除；遇到只有旧数据的会话目录时提示不支持，而不覆盖其中内容。
- `UserData` 是可配置的可写根目录：开发/便携模式默认使用模拟器目录中的 UserData；安装包由应用后端解析到可写位置后显式传入服务，不假定应用安装目录可写。具体开发与发行路径在实施计划中明确。
- QEMU 的 state-file 输出改为本次运行独立的 JSON 设备快照，正常退出后由应用后端校验并写入 session.json。QEMU 仍不解析 profile/session/settings。

实施时删除 `harness/profile.py`、`harness/launch.py` 及只测试旧应用逻辑的 `tests/test_profile.py`，替换旧 profiles，并以 docs/desktop/json-format.md 取代旧 docs/profiles.md。scripts/run.sh、probe.sh、run_sd.sh、run_sd_update.sh 和仓库父目录 run_backup_emu.sh 的旧 profile 入口须一并适配或明确移除，不能留下引用已删除模块的脚本。仍需这些入口时，使用轻量 Node 入口复用同一套 TypeScript 服务，不另写一套启动/配置逻辑。

Python `harness/gnw.py`、headless 命令、QEMU 外设回归测试，以及活跃的镜像/固件制作工具仍有独立用途，保留并使用测试隔离目录，不读取用户 JSON 会话，不复制应用业务。不以清理废弃实现为理由重写整个 pytest/工具生态。

QEMU 收到解析后的机器参数、绝对路径及临时通信端点，不负责 profile 格式或 ROM 选择器。

## 5. 业务 IPC

通过受限 preload API 提供加载 ROM、保存 ROM、关闭会话、输入变化和订阅状态事件。界面不能提交任意 QMP 命令或任意 Node 文件操作。所有来自界面的参数由应用后端再次校验。

请求具有 requestId；与运行实例有关的命令和事件具有 runtimeSessionId。runtimeSessionId 每次启动重新生成，与持久化 profile ID 分开。旧会话的帧、QMP 回调和退出事件不得更新新会话。

主进程只向界面发布可消费的业务状态：空闲、启动中、运行中、停止中、错误，以及当前 ROM 和错误信息。像素不放进 JSON 业务消息。

## 6. QMP 和输入

QMP 使用独立的本机连接，先完成 greeting 和 capabilities 协商，使用请求 ID 匹配响应，同时处理异步事件、超时及断线。宿主本机 TCP 是跨平台基线；通信端点只绑定 loopback，由每次运行的控制器管理。

| 操作 | 接口 |
|---|---|
| 按钮 | qom-set /machine buttons |
| 电量、USB 等状态 | 现有 QOM 属性查询 |
| 暂停/继续 | stop / cont |
| 设备复位 | system_reset |
| 正常退出 | quit，再等待进程退出 |
| 设备异常 | QMP 事件、进程退出事件、stderr |

输入管理器将物理键映射到 LEFT、UP、RIGHT、DOWN、A、B、TIME、GAME、PAUSE、POWER、START、SELECT 等设备语义，再生成现有位掩码。过滤操作系统自动重复。按钮掩码的不同转换按顺序发送，不合并掉短促的按下/松开。

未来多个输入来源按来源持有状态，合并后再提交。改键先清除旧状态；失焦、打开菜单/对话框、关闭及切换会话时释放输入。平台菜单焦点事件的可靠性必须实际检查，不能假定 DOM blur 覆盖所有情况。保留现有电量/USB 快捷键语义，通过设备属性控制，不依赖 QEMU 的宿主键盘映射。

UI 高亮未来可以立即反映请求状态，单独标识模拟器确认状态。QMP 成功只表示属性设置完成，不表示固件或画面已经响应。显示通道不接受输入，避免 QEMU 原生键盘输入与 buttons 掩码叠加而卡键。

设备复位与“重新启动 ROM”是不同操作：前者 system_reset，后者完整退出并再次启动同一 profile。Retro-Go 内某个游戏的重新开始由固件处理，不将 system_reset 命名为游戏重开。

## 7. 会话生命周期

状态机：空闲 → 启动中 → 运行中 → 停止中 → 空闲。失败进入错误状态，资源清理完成后允许重试。

启动：

1. 解析并校验 profile、镜像和 QEMU 可用性。镜像校验包括可读性、文件尺寸及后端实际支持的约束，不能只检查文件存在；相关规则以机器模型为依据，避免猜测固件兼容性。
2. 获取会话独占锁，准备工作副本和本次运行目录。state.json 每次运行使用独立路径，防止误读上次运行状态。
3. 准备独立 QMP/像素端点，使用参数数组启动 QEMU，不拼接 shell 命令；QEMU 以 -S 暂停启动。
4. 完成 QMP 协商和显示协议握手、监听端注册，初始化 buttons=0；此时只要求显示端准备好，不等待固件运行后的首帧。
5. cont 后等待有效首帧，进入运行中；启动过程设超时并可清理失败进程。

切换 ROM：先校验目标，新 ROM 无效时保持当前会话。校验成功后串行停止旧会话，再准备并启动新会话。新会话启动失败时显示错误，不声称旧会话仍在运行。启动/停止期间重复请求返回明确的 busy 状态，避免并发切换或隐含请求队列。

停止：释放输入 → 请求 quit → 等待进程退出 → 收集本次退出状态并原子更新 session → 关闭通道/接收端 → 释放会话锁。窗口关闭也执行同一路径，完成后应用退出。QMP 返回不是退出完成证据。

退出超时允许明确的强制终止处理，并告知用户无法确认正常退出与状态保存；已落盘镜像保留，不删除存档。进程崩溃清理端点和锁，不把旧 state.json 或无响应设备状态写成新的正常状态。

会话锁由所有复用 TypeScript 服务的入口共同遵守。保留的 Python headless 驱动使用测试隔离镜像，支持的入口不能绕过控制器去写应用管理的 UserData 会话。锁覆盖整个 QEMU 存活期，具备崩溃恢复和存活性核验；实现计划选择成熟的跨平台锁机制，不只依赖未验证的 PID 文件。主控进程崩溃而 QEMU 仍存活时，其他启动器仍不得回收锁或打开同一会话；恢复路径须核验关联的 QEMU 已退出，不能只核验主控 PID。

## 8. 完整帧 TCP 协议

使用独立 loopback TCP 连接；每次运行由应用后端创建监听端点，并将地址作为参数传给 QEMU 显示后端。QEMU 作为发送端连接，避免从日志解析端口。没有第二个原生显示窗口。协议独立于 GNW 设备模拟，第一版只支持一个控制台、一个客户端。

version=1 消息使用显式序列化的固定消息头，不发送 C 结构体原始内存。规定整数端序，头包含 magic、版本、消息类型、头长度及载荷长度；帧消息另含帧序号、宽、高、stride、像素格式和生成时间戳。具体字段宽度/偏移作为实施计划中的独立协议表固定，再由双方共同使用，不由两端分别猜测。

- 握手确认协议版本、RGBA8888 格式和消息大小上限；不支持的版本立即报错。
- RGBA8888 指内存字节顺序 R/G/B/A，alpha=255；第一版紧密行排列，stride=width×4。QEMU surface 的宿主像素布局由发送端转换，不假定 pixman 格式等于浏览器格式。
- 每帧是完整画面，载荷长度严格为 stride×height。接收端检查整数溢出、长度、尺寸与协商上限；第一版支持 1..2048 的宽高，单帧像素上限 16 MiB，与当前 LTDC 范围一致。
- 尺寸变化通过下一帧头描述，完整接收后再更换显示缓冲。
- 时间戳是明确标注的 QEMU 宿主单调时钟值，不使用固件虚拟时间来衡量宿主延迟。没有时钟校准时仅计算同源间隔，不能直接跨进程相减。
- TCP 分包/粘包、半帧断线必须由解析器处理。失败终止该显示连接并通知控制器，第一阶段显示故障走正常停止与错误提示，不实现自动重连；重新加载创建全新连接。

## 9. 刷新、背压和渲染

显示后端目标刷新间隔约 16.7 ms，持续变化画面目标约 60 Hz。必须通过 QEMU 显示监听刷新机制驱动实际 surface 更新，不能仅把 30 ms 更新的旧 surface 以 60 Hz 重发。首帧主动提供，暂停时保留最后一帧；连接就绪不依赖固件已经运行。

QEMU 非阻塞发送，模拟线程不等待 socket 可写。最多保留一帧正在发送和一帧最新待发送；已开始的帧必须完整发送，尚未发送的待发送帧可以替换。异步发送读取自身拥有的快照，不能读取正在被 QEMU 修改的 surface。

接收端完整解析消息，最多持有接收中帧和最新待交付完整帧。通过消费确认/单次在途交付约束 Electron 内部转发队列，不能只限制 TCP 接收端却让 IPC 消息无限积压。渲染端按 requestAnimationFrame 显示最新完整帧，静态画面可保持不重绘。

为避免内核 TCP 发送缓冲积压多帧，协议包含接收完成 ACK：同一时刻最多一帧已发送但尚未确认，另有一帧最新待发送。ACK 只确认完整接收，不表示已显示；Electron 内部的绘制消费确认单独限制 IPC 转发。控制和输入不经过这两种 ACK。

第一版 Canvas/WebGL 渲染选一种简单可验证的路径，测量像素转换、接收端到渲染端复制和上传成本。初始不增加共享内存、压缩、增量更新、视频编码或多控制台。协议版本允许以后替换传输实现，业务 IPC/QMP 职责不随之改变。

## 10. 音频与跨平台交付

音频继续由 QEMU 播放，Electron 控制开关，不增加跨进程 PCM 通道。macOS 现有播放行为需要回归；Windows/Linux 的宿主播放通过 QEMU 跨平台音频后端接入，保持 SAI 生成及固件时序逻辑。

跨平台完成的声明须有三平台 QEMU 构建和真实窗口运行证据，包括有声游戏；不能只以 TypeScript 编译通过或 Electron 能启动作为证据。构建脚本中现有 Homebrew/macOS 假定在实施计划中单独列出，进行必要的定向适配，不重构外设或所有构建工具。

## 11. 验收与验证

- 从有效 profile 加载原厂 Mario/Zelda，画面、背光、声音和现有按键正常；原始镜像不变。
- 制作原厂双镜像和可选 Bank 2/SD 的 JSON profile；保存后可重新加载，源镜像相对路径及新格式会话存档正确。不要求旧文件/旧存档可用，旧格式应明确拒绝。
- 取消加载/保存不改变运行会话；无效 ROM 不关闭现有游戏；保存失败不产生被当成成功配置的半成品。
- 持续方向键、组合键、短点击、失焦及系统菜单/对话框不丢释放事件，不残留卡键。
- 连续加载、关闭窗口、启动失败、QMP 断线、像素断线、QEMU 崩溃和退出超时正确清理；第二个启动器不能同时写同一会话。
- 调整窗口及模拟尺寸变化保持正确比例、颜色和最近邻采样；检查高 DPI 屏幕的 CSS 尺寸与实际像素尺寸。
- 在 60 Hz 或更高刷新率显示器上，320×240 持续变化画面目标约 60 次有效更新/秒；报告实际 FPS、帧龄和丢帧，而不以重复绘制相同帧充数。
- 慢接收/慢渲染时内存和排队帧数有界；恢复后显示最新画面，不播放积压的历史画面；同时验证 QMP 仍响应。
- 测量输入到可见变化的整体延迟，以及协议/复制/渲染各段耗时。整体延迟使用可观察画面变化或独立测量，不把 QMP 响应时间当作整体延迟。目前不承诺尚未测量的数值上限。
- JSON 结构与持久化、生命周期失败路径、协议分包/背压/尺寸校验使用有意义的自动化测试；真实显示、系统菜单焦点、音频和延迟使用运行验证。
- 废弃 Python 应用模块、旧 TOML 示例与对应测试删除后，没有活跃脚本、入口或文档仍引用它们；保留的 QEMU Python 回归测试仍可运行。

## 12. 实施顺序与当前边界

后续实施计划按依赖顺序组织：固定协议表与新 JSON 数据模型 → QEMU 显示后端、退出快照与最小接收验证 → TypeScript 文件/QMP/会话服务 → Electron 主窗口及加载/制作菜单 → 删除废弃应用实现并更新受影响入口 → 三平台运行、输入/生命周期和性能验证。

工程初期建立 Pino 日志与自动化契约；窗口/表单形成后实现可连接已运行应用的 UI 操作及读取接口；每个对应任务同步更新独立文档。详细验收包含真实 UI 路径、CLI/JSON-RPC 和日志输出控制，参见补充设计。

这是设计级顺序，不是已开始执行的代码。共享内存、VNC/WebSocket 替代、键位编辑 UI、手柄 UI、按键可视化、存档管理器、机身外观和调试界面均不在第一阶段实现范围。用户已确认 UI 流程并要求美观现代，当前进入具体实施规划；编写计划不代表开始编码。
